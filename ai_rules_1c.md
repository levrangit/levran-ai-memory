# ai_rules_1c

## Назначение

Этот файл фиксирует, что должно происходить, когда AI-агент начинает работу с проектом:

`/home/leo/1c-akk`

Проект установлен из `ai_rules_1c`, профиль `other`, версия исходников при установке: `f214134`.

Важно: `ai_rules_1c` — это не самостоятельный AI-агент. Это набор правил, skills, commands, agents и MCP-конфигурации, которые задают агенту порядок работы: какие источники использовать, как исследовать конфигурацию 1С, когда можно менять код и как проверять результат.

## 1. Вход в проект

При обращении агента к:

`/home/leo/1c-akk`

проект предоставляет:

- `AGENTS.md`
- `USER-RULES.md`
- `memory.md`
- `LLM-RULES.md`
- `.dev.env`
- `.ai-rules.json`
- `.ai-agent/rules/`
- `.ai-agent/skills/`
- `.ai-agent/agents/`
- `.ai-agent/commands/`
- `.ai-agent/mcp.json`

Агент не должен автоматически загружать все rules и skills в контекст. Они подключаются по соответствующим триггерам и типу задачи.

## 2. Базовые правила

Точка входа — `AGENTS.md`.

Он задаёт общий порядок работы и требует учитывать:

1. `USER-RULES.md`
2. `memory.md`
3. `LLM-RULES.md`

Модельный профиль из `.dev.env` может выбирать дополнительный файл вида:

`.ai-agent/rules/model-<slug>.md`

При этом модельный профиль не отменяет обязательные правила проекта.

## 3. Определение типа задачи

Перед активной работой агент определяет характер задачи (triage). В документации предусмотрены, в частности:

- Quick-fix
- Docs-fix
- Spec-authoring
- Full-cycle

Для выбора глубины проверки учитывается `.ai-agent/rules/verification-policy.md`.

## 4. MCP-first для задач 1С

Для содержательных и рискованных задач по 1С агент должен сначала ознакомиться с:

`.ai-agent/rules/mcp-policy.md`

и соответствующим skill:

`.ai-agent/skills/mcp-1c-tools/SKILL.md`

MCP рассматривается как основной источник фактов о конфигурации и окружении, а не как необязательное дополнение.

В зависимости от задачи выбирается соответствующий маршрут:

- поиск кода — `1c-code-search`
- метаданные — `1c-meta-info`
- зависимости/влияние — `1c-impact`
- формы — `1c-form-inspect`
- валидация — `1c-validate`
- документация платформы — соответствующий documentation route
- шаблоны — template search
- живая информационная база — live-IB route
- управление метаданными — metadata-management route

## 5. Принцип bounded search

Поиск не должен превращаться в бесконечное сканирование конфигурации.

Правила требуют, чтобы каждый вызов инструмента закрывал конкретный информационный пробел.

Типовая логика:

```
неизвестен X
   ↓
конкретный MCP-вызов
   ↓
получен X
   ↓
определён следующий неизвестный Y
   ↓
следующий вызов
```

А не многократный повтор одного и того же поиска без изменения входных данных.

Для поиска действует предусмотренный проектом маршрут:

graph → code/metadata → native route

с ограничением области поиска.

## 6. Проверка возможностей платформы

Если вопрос касается того, умеет ли платформа 1С определённое действие, агент сначала должен проверить официальную/доступную документацию и существующие механизмы.

Предпочтительный порядок:

1. documentation/capability search;
2. подробности найденного механизма;
3. при необходимости поиск по БСП;
4. поиск существующей реализации;
5. собственный код только там, где он действительно нужен.

Это предотвращает написание собственного решения для уже существующего механизма платформы или БСП.

## 7. Поиск существующего решения перед написанием кода

Перед новой реализацией агент должен проверить:

- существующий код проекта;
- существующий механизм конфигурации;
- механизмы платформы;
- БСП;
- существующие шаблоны и паттерны.

Предпочтение отдаётся существующему коду и штатным механизмам.

## 8. Работа с памятью

Для нетривиальных задач применяется принцип Recall-first.

Агент должен попытаться найти существующий проектный контекст/память до проектирования решения.

Если пользователь в ходе работы исправляет решение, такая коррекция рассматривается как значимое изменение требований и должна учитываться дальше; правила проекта предусматривают capture таких коррекций.

## 9. Изменение кода

Если задача требует изменения BSL или другого артефакта, ожидаемый цикл выглядит так:

```
получить задачу
    ↓
прочитать применимые rules
    ↓
определить тип задачи
    ↓
исследовать метаданные
    ↓
исследовать существующий код
    ↓
проверить API/механизмы платформы
    ↓
найти подходящий шаблон/паттерн
    ↓
спланировать изменение
    ↓
внести изменение
    ↓
провести проверку
    ↓
сообщить результат
```

Агент не должен переходить непосредственно от пользовательского требования к генерации кода, если для задачи требуется предварительное исследование.

## 10. Проверка BSL

После изменения BSL предусмотрена цепочка проверки, в зависимости от применимого уровня:

```
syntaxcheck_file
    ↓
check_1c_code
    ↓
review_1c_code
```

Конкретная глубина зависит от verification policy и бюджета проверки.

Фраза «код выглядит правильно» не заменяет предусмотренную инструментальную проверку.

## 11. Проверка XML

При изменении XML применяется соответствующая XML-проверка, в частности:

`verify_xml`

Результат изменения должен быть проверен после записи.

## 12. Изменение метаданных

Изменение метаданных 1С отличается от обычного редактирования BSL.

Для таких задач используется маршрут управления метаданными, который должен учитывать:

- схему объекта;
- существующие связи;
- формы и контекст;
- корректность XML/структуры;
- итоговую валидацию.

Ручное изменение XML не является универсальной заменой штатному механизму управления метаданными.

## 13. Работа с живой информационной базой

Для live-IB операций используются предусмотренные проектом процедуры и skills.

Правила запрещают подменять предусмотренный маршрут произвольными командами `1cv8.exe`/`ibcmd`, если для данной операции уже существует штатная процедура.

Это особенно важно для операций, которые могут изменить живую информационную базу.

## 14. MCP-серверы проекта

В установленном проекте `.ai-agent/mcp.json` содержит 7 MCP-серверов:

1. `1c-code-metadata-mcp`

5. `1c-graph-metadata-mcp`

Их назначение соответствует основным этапам: метаданные, поиск/код, синтаксис, документация, шаблоны, проверки и БСП/SSL.

## 15. Что находится непосредственно в /home/leo/1c-akk

`/home/leo/1c-akk` — это проектная оболочка правил и инструментов, а не сама выгрузка конфигурации 1С.

То есть наличие каталога проекта не означает наличие в нём `Configuration.xml`.

Сама конфигурация может предоставляться через соответствующий MCP-контур.

Для текущей инфраструктуры отдельно существуют MCP-контуры для:

- 1С:Документооборот (DO + DO_RAU);
- 1С:ERP (ERP + ERP_RAU).

## 16. Практический пример трассы

Для запроса:

> «Найди в конфигурации Документооборот объект Документ.Задача и покажи его структуру. Ничего не изменяй.»

ожидаемый процесс:

```
1. Агент получает задачу.
2. Определяет, что это исследовательская read-only задача.
3. Читает применимые проектные правила.
4. Учитывает USER-RULES и memory.
5. Загружает MCP policy.
6. Загружает соответствующий MCP skill/router.
7. Определяет нужный metadata/code инструмент.
8. Выполняет конкретный MCP-вызов.
9. Получает факты о Документ.Задача.
10. При необходимости делает следующий ограниченный вызов.
11. Формирует ответ только на основании полученных данных.
12. Ничего не изменяет.
```

## 17. Главная идея архитектуры

Вся система должна работать не по принципу:

```
пользователь → LLM → сразу код
```

а примерно так:

```
                 ПОЛЬЗОВАТЕЛЬ
                       │
                       ▼
                  AI-АГЕНТ
                       │
             ┌─────────┴─────────┐
             ▼                   ▼
        PROJECT RULES          SKILLS
             │                   │
             └─────────┬─────────┘
                       ▼
                  MCP ROUTING
                       │
        ┌──────────────┼──────────────┐
        ▼              ▼              ▼
     metadata         code           docs
        │              │              │
        └──────────────┼──────────────┘
                       ▼
                 1С-КОНФИГУРАЦИЯ
                       │
                       ▼
                   ПРОВЕРКА
                       │
                       ▼
                    ОТЧЁТ
```

Ключевой принцип: сначала получить проверяемые факты из конфигурации, документации и существующего кода, затем принять решение о реализации, а после изменения — провести предусмотренную валидацию.
