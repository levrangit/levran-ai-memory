# blitcp — анализ вариантов передачи файлов

Дата анализа: 2026-09-26

Репозиторий проекта: https://github.com/gekap/blitcp

## Назначение

blitcp — высокоскоростной инструмент копирования файлов с поддержкой дедупликации, оптимизации порядка чтения/записи, удалённых передач и облачных хранилищ.

## Варианты передачи

### 1. Локальный компьютер → локальный компьютер

Поддерживается передача между локальными путями Windows/Linux.

Основной режим для локальных файлов — параллельная обработка небольших файлов (--small-files parallel). Есть также потоковый режим (--small-files stream), использующий tar-поток.

### 2. Локальный компьютер ↔ удалённый Linux по SSH

Поддерживаются оба направления:

- local → remote;
- remote → local.

Для SSH blitcp использует потоковую передачу через SSH/tar. В changelog проекта указано, что начиная с версии 2.3.0 raw SSH tar streaming заменил SFTP для удалённых передач. Также поддерживается remote → remote.

### 3. Удалённый компьютер → удалённый компьютер

Поддерживается передача между двумя SSH-источниками/назначениями через локальный компьютер как relay.

### 4. SMB/CIFS

В репозитории предусмотрена поддержка SMB/CIFS. Для неё в дополнительных зависимостях используется smbprotocol>=1.10.

Это потенциально интересно для Windows ↔ Linux, если на Linux настроена Samba.

### 5. S3 / S3-compatible storage

Есть поддержка объектного хранилища через boto3 (boto3>=1.28).

### 6. Azure Blob Storage

Поддерживается через azure-storage-blob>=12.0.

### 7. Google Cloud Storage

Поддерживается через google-cloud-storage>=2.0.

### 8. Передача одного файла

Источник или назначение может быть отдельным файлом, а не только каталогом. Это удобно для изолированных тестов канала передачи.

## Режимы работы с небольшими файлами

--small-files parallel — параллельная передача небольших файлов; режим по умолчанию для локальных передач.

--small-files stream — потоковая передача небольших файлов через tar. Для SSH удалённых передач tar streaming используется независимо от этого параметра.

## Инкрементальная проверка и принудительное копирование

Важное различие параметров:

- --overwrite — копирует каждый файл без проверки, является ли он уже идентичным в назначении. Это основной параметр, если нужно избежать пропуска одинаковых файлов.
- --no-cache — отключает постоянный SQLite-кэш хешей, но не отключает сканирование назначения.
- --no-dedup — отключает content-aware deduplication, но не отключает инкрементальную проверку существующих файлов.
- --no-verify — отключает посткопировочную проверку, но также не отключает первоначальную инкрементальную проверку.

Если проблема состоит именно в длительной фазе:

    Phase 2b — Incremental check
    Checking destination for existing files...

то --no-cache, --no-dedup и --no-verify сами по себе эту фазу не устраняют. Для проверки поведения следует отдельно протестировать --overwrite.

## SSH и дополнительные параметры

Полезные параметры:

- --threads N — число рабочих потоков;
- --hash auto|xxh128|sha256 — алгоритм хеширования;
- --no-cache — без постоянного hash cache;
- --no-dedup — без content-aware deduplication;
- --no-verify — без посткопировочной проверки;
- --overwrite — принудительно копировать файлы;
- --force — пропустить предварительную проверку свободного места;
- --log-file PATH — записывать лог;
- -p / --progress — показывать прогресс;
- -v / --verbose — подробный вывод;
- -q / --quiet — минимальный вывод;
- SSH compression (-z / --compress) — сжатие SSH; для быстрой локальной сети документация не рекомендует включать его без необходимости.

## Тест для SSH без изменения проекта

Текущий upload_4.ps1 использует:

    --no-verify --no-cache --small-files parallel --threads 16

Но это не отключает incremental check.

Для отдельного ручного теста имеет смысл проверить:

    blitcp -p --overwrite --no-dedup --no-cache --no-verify ...

Это именно тестовый вариант. В GitHub-скрипт upload_4.ps1 изменение не вносится без отдельного разрешения.

Это подтверждает работоспособность локального blitcp → RDP/SMB-пути для тестового файла.
